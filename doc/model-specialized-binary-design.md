# 面向单用户的模型专用二进制

本文说明专用二进制的目标、当前实现和下一步工作。当前已实现的范围以 [Qwen3.5 入口契约](../crates/apxinf-qwen35/CONTRACT.md)为准，实测依据见 [v2 结果](../benchmarks/specialization/v2/RESULTS.md)。本文提出的 EngineTailor 集成和后续性能优化不属于已交付能力。

## 目标与取舍

目标是让一个本地用户在指定 Apple Silicon 设备上，以约定的输出质量获得尽可能短的等待时间。重点是首次可见文字、长回答的持续解码速度，以及完整回答耗时。启动成本单独衡量；常驻进程能摊薄启动成本，但不能代替一次启动场景的测试。

“最小”和“最快”是相关但不同的目标。删除无关模型和工具可以减少编译、链接及分发工作。如果这些代码原本不参与推理，删除它们通常不会改变每个 token 的计算与访存。持续解码的优化必须针对实际执行的算子、数据移动、同步和调度，不能从二进制变小推导出来。

每个交付目标由一个固定 profile 定义。它至少绑定模型 revision、资产摘要、硬件范围、执行精度、量化方式、生成规则、输入范围和质量要求。同一个模型在不同硬件或精度下可以有不同的 profile，也可以有多个独立二进制。“每个模型一个二进制”不等于让所有模型共用一个带动态注册表的程序，也不等于只支持一个固定 prompt。

在这个目标下，离线工作可以较重。构建阶段完成依赖选择、候选评估和资产准备；用户得到已选定的实现。运行阶段仍须检查输入范围与资产身份，但不需要安装优化工具或重新搜索实现。

## 开发和交付边界

建议按下表划分职责。第一列的职责定义集成方向，不代表当前两仓库已实现自动接入。

| 环节 | 职责 | 与用户运行环境的关系 |
|---|---|---|
| EngineTailor 离线优化 | 固定目标与质量约束，记录候选选择、实验计划、测量和反馈，保存产物身份 | 不进入用户的推理依赖 |
| ApxInf 执行库 | 提供模型、权重加载、tokenizer、CPU/Metal 算子和状态管理的原生实现 | 所需代码编译进交付程序，或成为明确声明的运行依赖 |
| 模型专用入口 | 绑定一个 profile，只暴露该目标需要的输入与输出，拒绝不支持的选择 | 用户直接启动它 |
| 构建与验证流程 | 选择 features，编译原生程序，检查编译范围，验证最终产物，形成 manifest | 只在开发或发布环境运行 |
| 用户交付包 | 可执行文件、必要资产、许可证与依赖说明 | 不要求 EngineTailor、Python 或 Rust 工具链 |

EngineTailor 的实验计划描述“准备验证什么假设”。运行时执行计划描述“这个模型按什么顺序执行”。两者不能混用，也不能把实验计划获准执行解释为候选实现已通过正确性或性能验收。

可复用 EngineTailor 的离线编排、计划、测量与证据管理能力，把选中的目标交给 ApxInf 原生构建流程。集成记录应同时绑定目标 profile、候选源码、构建参数、质量证据和可执行文件摘要。仅有源码导出或离线选择结果，不能证明已经生成可运行的原生二进制。目前 Qwen3.5 专用入口由 ApxInf 的 Cargo package 和比较脚本构建，尚未打通 EngineTailor 自动交付该产物的流程。

不结合 EngineTailor 也能继续工作：开发者可以直接固定契约、选择 Cargo features、运行同一组验证并保存证据。EngineTailor 的价值在于管理多次优化决策与反馈；它不是这个原生程序的运行前提。若以后更换 ApxInf 的执行实现，应另设运行时对照，不能把更换实现的收益归因于编译裁剪。

## “不参与编译”如何证明

这里区分三件事。

| 操作 | 含义 | 证据 |
|---|---|---|
| 编译排除 | 编译器不处理不需要的源码或资源 | Cargo features、Rust `.d` 依赖文件、原生编译输入、对象文件和 shader 资源记录 |
| 链接剔除 | 源码已经编译，链接器随后移除未使用部分 | 链接输入、符号、链接映射和最终文件 |
| 分发排除 | 某些文件不放进用户交付包 | 交付清单、运行依赖与实际文件访问检查 |

最终文件中没有某个符号，不能单独证明对应源码没有编译；包里没有源码也不能证明编译排除。Rust 编译命令主要显示 crate 入口，因此还要看 `.d` 文件中的实际模块。原生桥接和 shader 资源则需要分别确认，不能只查看 Rust feature 声明。

当前实现用正向 features 选择所需组件。专用 package 关闭通用依赖的默认 features，明确保留 Qwen3.5、SafeTensors 和 Metal head/MLP。`general-reference` 恢复通用组件，供同一个入口对照。专用 package 应单独构建；全 workspace 构建可能合并其他 package 请求的 features，扩大实际编译范围。

这不是为每个模型复制一套库。共享实现仍保留在 ApxInf 中，由编译选择确定本次需要哪些部分。新实现、测试和 fixture 均手写，调用已有依赖的公开 API；专用化流程不授权复制外部实现，也不引入代码生成器。

## 当前 Qwen3.5 已实现什么

`apxinf-qwen35-08b` 绑定 `qwen35-0.8b-f32-metal-w8-head-mlp-v1`，模型为 `Qwen/Qwen3.5-0.8B`，revision 为 `2fc06364715b967f1860aea9cf38778875588b17`。主体仍使用 CPU/Accelerate F32；head 和全部 24 层 decode MLP 使用现有 Metal W8 路径。这不是全 GPU 推理实现。

当前只支持 macOS Apple Silicon 上的单用户文本生成，batch 和并发均为 1，总上下文上限为 2048 token。生成沿用现有 greedy 规则和聊天 tokenizer EOS 248046。配置中的 EOS 248044 不控制当前聊天生成终止；该差异曾使早期运行失败，最终 r3 修正并验证了兼容行为。

入口提供普通流式文本、单次 JSON 和常驻 JSONL。普通输出通过已有 tokenizer 的增量解码 API 输出完整文字片段，结束时与完整解码核对并补尾。JSON 模式用于完整结果与测量，计时不含结果序列化和输出写入。已有 `ttft_ms` 表示首 token 回调时间，不等于用户看见首段文字的时间。

常驻模式在每次请求前重置模型状态，不共享聊天历史或前缀缓存。运行时校验五个必要资产的 SHA-256，并直接打开固定 SafeTensors shard；不需要分片索引，也不加载视觉张量。权重仍在外部文件中，运行期间资产内容必须保持不变。

本轮完成了以下编译排除：

- 保留 Qwen3.5，排除 Llama、Qwen3-VL、PI0.5、注册表、VLA 和 debug 模块。
- Metal 桥接对象由 10 个减少到 2 个，只保留 head 和 MLP；MatVec 与实验模块不进入最小构建。
- 排除 GGUF、通用 CLI 的 clap、tokenizer 进度条和 C++ 训练代码。

公共 core 的算子尚未进一步拆分。第三方 tokenizer 仍含上游没有可选 feature 开关的 Rust 代码。模型维度与组网仍由现有配置和执行实现处理，尚未变成离线固定的执行计划。Metal shader 仍以内嵌源码交付，在模型构造阶段由 Metal 编译。

“单个原生可执行文件”描述主程序，不表示把所有权重与系统库压进一个文件。当前程序为 7,267,376 bytes，五个外部资产合计 1,759,777,953 bytes；此外依赖 macOS 的 Metal、Foundation、Accelerate 和系统动态库。把权重嵌进主程序只是另一种包装方式，不能据此承诺更小内存或更低延迟。

## 当前结果能支持哪些结论

公开的 [v2 结果说明](../benchmarks/specialization/v2/RESULTS.md)采用最终 `model-specialization-v2-20261010-r3`，未把早期准备或失败记录计入结果。完整计时边界见[比较契约](../benchmarks/specialization/v2/contract.json)，执行方法见[比较流程](../benchmarks/specialization/v2/README.md)。

| 观测 | 本轮结果 | 可以支持的结论 |
|---|---|---|
| 同一专用入口的干净编译 | reference 40.85 s，minimal 33.23 s，两次中位数 | 在本机条件下，组件裁剪减少了约 18.7% 的构建耗时 |
| 同一专用入口的文件大小 | reference 7.536 MB，minimal 7.267 MB，十进制 | 组件裁剪减少了约 3.57% 的文件体积 |
| 对照通用 CLI | minimal 编译耗时减少 23.9%，文件体积减少 18.7% | 这是入口简化与组件裁剪的合并效果 |
| 英文长回答 | 212 个输出 token，reference 29.59、minimal 31.56 token/s | 观测差异为 +6.68%，但不能认定稳定加速 |
| minimal 启动阶段 | 两次为 5.94 s 和 6.80 s | 本轮没有显示启动收益 |

构建使用相同 release 设置、SDK、依赖版本和独立 target 目录，操作系统文件缓存没有控制。运行比较只在两个专用构建之间保持相同入口与计时边界；通用 CLI 用于输出 token 和 prompt 长度对照，其协议未提供完整 prompt token 身份。

驻留比较共 80 个请求，其中 48 个参与性能统计，每种构建只有两个独立进程。输入 token、输出 token、文字、终止原因及执行路径在两个专用构建间一致。长回答吞吐范围重叠，测量区间还出现了全系统 swap-in，不能把观测差异归因于组件裁剪。最终记录保留 `formal_performance_accepted=false`。

这些结果证明当前交付能运行，并且确实缩小了编译范围。它们不证明所有模型都已支持，也不证明全局最小体积或设备极限性能。后续变更需要绑定新的源码和产物，不能沿用旧结果作为新二进制的验收证据。

## 下一步分别验收

以下四项均是后续方向，当前实现尚未完成。它们可以共享目标 profile 和证据格式，但每项应有独立对照，避免把不同来源的收益混在一起。

| 方向 | 要实施的变化 | 验收内容 |
|---|---|---|
| 启动权重预打包 | 离线提取所需文本权重，生成固定布局与 W8 数据，减少每次启动的装载和准备工作 | 绑定原始与转换后资产摘要；检查尺寸、布局、数值和输出；分别测转换成本、交付大小、资产校验、加载和模型构造时间 |
| 固定执行计划 | 针对固定层数、维度、布局及已声明输入范围，离线确定执行顺序、缓冲区和必要算子 | 检查每种支持形状、状态重置和内存边界；证明新增源码排除；比较相同精度的输出与生成耗时，拒绝范围外输入 |
| CPU/GPU 数据驻留与同步 | 先测每 token 的数据移动、等待和 dispatch，再选择减少同步、持续驻留、融合或迁移路径 | 明确异步完成边界；记录同步次数、传输量和时间；保持相同算法与质量要求，分别测首 token、持续解码和完整回答 |
| Metal AOT | 预先编译 shader，并按设备与 pipeline 条件评估进一步准备或缓存 | 区分库加载、pipeline 创建、运行时编译和首次 dispatch；记录 SDK、硬件、覆盖范围与回退；检查兼容性、正确性和冷启动收益 |

权重预打包不等于取消资产校验。当前启动中资产校验中位数约 3.58 秒，模型构造约 2.58 秒，优化准备工作后仍需计入身份检查成本。若以后改变校验策略，应单独修改契约并说明新的信任边界。

Metal AOT 也不是一个只由文件扩展名决定的结论。预编译库、函数特化、pipeline 创建和设备相关缓存是不同阶段。下一项实现必须说明完成了哪些阶段，以及是否仍有运行时编译或未覆盖的 pipeline；不能承诺任意设备通用或完全消除驱动准备成本。

## 可复用的开发流程

下面是仓库内可审阅的工作约定，供人工或技能驱动的开发复用。它不依赖某台机器安装的技能文件，也不包含技能实现。当前比较脚本落实了其中一部分；其他模型仍需先补齐自己的契约与入口。

1. **固定目标。** 记录模型 revision、资产摘要、硬件、精度、输入范围、质量门槛和用户关心的时间边界。
2. **追踪必要组件。** 从公开推理入口检查组网、加载、tokenizer、算子、状态和资源访问，说明保留或排除理由。
3. **选择最小实现范围。** 使用明确的编译开关与专用入口；先验证依赖关系，再排除注册表、后端或实验路径。
4. **完成结构与错误检查。** 在 CPU 测试中验证参数、资产身份、上下文拒绝和状态重置，并检查各 feature 组合是否可编译。
5. **冻结对照。** 在测量前保存源码快照、构建参数、工作负载与样本计划。配置变化使用新记录，保留失败过程。
6. **检验实际产物。** 使用独立构建目录，记录文件摘要、编译输入和运行依赖；通过交付程序本身比较输入、输出和执行路径。
7. **分开报告成本与性能。** 分别报告干净编译、受控改动重建、文件及资产大小、启动、首 token、持续解码与完整请求耗时。GPU 测量独占设备并记录噪声条件。
8. **形成交付记录。** 保存 profile、manifest、正确性结果、性能状态、依赖许可及重建命令。未测或未通过的项目保留原状态，不用文件变小代替性能结论。

对新模型的首个成果应是可检查的目标契约和原生入口，而不是“任何模型都能自动生成最快程序”的承诺。可复用的是选择、验证和交付方法；每个 profile 的正确性与性能仍需用其实际产物证明。
