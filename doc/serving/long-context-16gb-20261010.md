# 16GB 统一内存上的 64K–128K 完整上下文方案

日期：2026-10-10。状态：设计提案，尚未实现或通过长上下文验收。

目标是让当前 Qwen3.5-2B 文本 serving 处理 64K–128K 上下文，并保留完整原文。本文把用户所说的 16G 共享存储解释为 Apple Silicon 的统一内存。K 表示 1024 tokens，GiB 表示 1024³ bytes。上下文长度包含模板、工具定义、输入和输出预留。

建议先交付经过验证的 64K 单请求服务，再以独立配置验证 128K。优先保留当前 BF16 权重和完整注意力缓存。只有容量或延迟测量表明需要时，才引入量化或可恢复前缀缓存。摘要、检索替代原文、滑动窗口和自动精度切换均不属于这条默认路径。

本提案从[系统设计](../serving-system-design-20261009.md)和[实施计划](implementation-plan.md)细化长上下文工作。现有[契约](contracts-v0.1.md)仍有最高优先级。本文没有改变协议、运行时版本、模型文件或部署默认值。

## 当前能支持什么

| 项目 | 代码现状 | 对目标的影响 |
| --- | --- | --- |
| 上下文 | 默认 16,384，部署参数最多 131,072 | 已有 64K／128K 参数范围，不代表这些长度已经验收 |
| 模型位置配置 | 当前 bundle 为 262,144 | 模型配置不能越过服务协议和部署限制 |
| 长度检查 | 准备后的输入长度加最大输出 allowance 不超过部署窗口 | 128K 窗口不能同时容纳 128K 输入和额外输出 |
| 活跃请求 | 一个 worker 只执行一条序列 | 符合 16GB 的初始容量目标，后续请求需要排队 |
| Prefill | 默认每块 256 tokens，块间检查控制消息 | 已能限制每次计算的输入块，但完整 KV 仍随历史增长 |
| 内存准入 | 默认预算 10GiB，每请求固定预留 1GiB | 没有按输入、输出和 chunk 计算请求峰值 |
| 请求状态 | 每请求创建缓存，结算后释放 | 多轮长原文目前会重复 prefill |
| 缓存能力 | 没有 KV 量化、prefix restore 或 SSD 状态恢复 | 这些能力需要单独实现和验收 |
| 请求时限 | 默认 300 秒，从入队开始，配置最多 3600 秒 | 长 prefill 可能先达到 deadline，排队也消耗这段时间 |
| 传输 | HTTP body 上限 1,000,000 bytes，worker frame 上限 1MiB | token 长度合法不保证消息、工具和 JSON 编码后的字节数合法 |

代码依据：[启动参数](../../crates/apxinf-serving/src/main.rs#L32)、[固定预留](../../crates/apxinf-serving/src/supervisor.rs#L107)、[上下文检查](../../crates/apxinf-serving/src/supervisor.rs#L1342)、[worker 生成](../../python/apxinf/apxinf/serving/text_worker.py#L181)、[HTTP 限额](../../crates/apxinf-serving/src/gateway.rs#L66)。

现有专项内存证据只达到实际缓存位置 37。更长阶段在模型加载后被 host pressure 门阻断。它证明短请求的状态释放，不能批准 16K、64K 或 128K 的峰值上界。此前串行服务和客户端功能测试也不能替代这个容量验收。详见[内存实测记录](memory-evidence-20261010.md)。

## 容量推导

当前文本路径的权重逻辑大小约为 3.505GiB，加载时 allocator active 与它接近。模型有 18 层固定大小的循环状态，只有 6 层保存完整注意力 KV。不能按 24 层普通 Transformer 的 KV 公式估算它。

对当前 BF16、单序列、新建缓存、chunk=256 的路径：

```text
固定循环状态 = 19,537,920 bytes
BF16 KV 每位置字节数 = 6 × 2 × 2 × 256 × 2 = 12,288 bytes
A(N) = 256 × ceil(N / 256)
请求状态 = 19,537,920 + 12,288 × A(N)
```

N 是实际消费位置，A 是已分配的 KV 容量。其他 chunk 配置需要按实际扩容路径处理尾部余量。准入使用最大输出预留，并覆盖取消时尚未公开的预计算位置，不能仅使用已返回给客户端的输出数。

| 总上下文位置 | BF16 KV | 固定状态加 KV | 文本权重加上述状态 |
| --- | --- | --- | --- |
| 16,384 | 192MiB | 0.206GiB | 3.711GiB |
| 32,768 | 384MiB | 0.393GiB | 3.898GiB |
| 65,536 | 768MiB | 0.768GiB | 4.273GiB |
| 131,072 | 1,536MiB | 1.518GiB | 5.023GiB |

这些是静态逻辑组成项，不是进程峰值，更不是整机占用。它们不含 prefill workspace、KV 扩容期间的旧新数组重叠、运行时和编译开销、CPU 消息对象、allocator 保留、系统及其他应用。完整推导及首块实测见[缓存几何记录](qwen35-memory-geometry-20261010.md)。

因此，16GB 容量本身没有排除这个 2B 模型的 128K 路线，但当前代码和证据尚不足以承诺稳定运行。128K 的请求状态本身就超过默认 1GiB 预留，必须先修正准入。64K 也不能仅凭状态小于 1GiB 判断足够，因为临时空间还没有计入。

## 第一阶段：完整 BF16 上下文与容量准入

继续使用 Rust 控制面和现有 MLX worker。保留单个活跃请求，暂不加入连续批处理，也不新增独立调度进程。首次交付只需要一个按执行配置查询的内存估算器，以及现有准入和观测的扩展。

```mermaid
flowchart LR
    A[完整原文与工具定义] --> B[模板与分词]
    B --> C[上下文及传输限额检查]
    C --> D[按输入 输出预留 chunk 查询容量]
    D --> E[原子取得请求容量]
    E --> F[单序列分块 prefill 与生成]
    F --> G[同步及资源结算]
```

分词前保留有界的准备阶段容量。得到真实 token 数后，在提交生成前检查完整请求容量。不能先产生大型张量，再发现预算不足。等待容量期间不持有用于生成的 compute permit。

预算按互不重复的类别计算：

```text
服务占用估计 = 模型常驻 + 请求状态 + 执行临时峰值
             + 运行时余量 + CPU 与传输缓冲 + 已保留的快照

服务占用估计 <= 服务预算
服务预算 + 系统和其他应用预留 + 安全余量 <= 物理内存
```

设计起点为服务预算 8GiB，系统与应用预留 6GiB，另留 2GiB 余量。这是待测预算划分，不是证明当前桌面应用仅占 6GiB，也不是建议直接把 CLI 改为 8GiB 后宣告完成。若应用占用更高，服务预算相应下降。只在实测支持时考虑把服务预算提高到 10GiB。

现有 `memory_budget_bytes` 同时参与账本和 MLX allocator guideline，不能直接代表含 CPU 对象在内的整服务硬上限。实现时保留明确的总预算和 MLX 分配预算关系。现有 allocator active、cache、peak、缓存 payload 与进程 footprint 分开观察，不把重叠计数直接相加。

准备阶段保留现有 host pressure 检查，生成派发前再次检查。活跃请求中压力升高的行为继续服从 HP-04，不擅自改为自动中止。若希望增加运行中内存熔断，需要先定义契约和明确终态；现有压力门不提供这项保护，也不能抵御其他应用突然大量分配造成的所有风险。

建议的最小内部接口如下。字段定义属于后续契约工作的输入，尚不是新 wire format。

| 接口 | 输入与输出 | 边界 |
| --- | --- | --- |
| 内存配置记录 | 模型和运行时身份、精度、chunk、P/G 适用范围、估算参数、校准记录摘要 | 配置变化使旧记录失效。未测长度不能静默外推为已支持 |
| 请求容量估算 | 输入 P、最大输出 G、执行配置，返回所需字节及依据 | 同时计入状态容量、扩容和实测 workspace，检查整数溢出 |
| 容量准入 | 所需字节、现有账本、压力样本，返回预留或拒绝 | 原子记账，pending reclaim 仍占预算 |
| 部署能力发布 | 发布已批准的 `max_context` 和固定执行身份 | 宣布 64K 不等于一次 64K 请求通过，要覆盖批准的输入／输出范围 |

错误沿用已有分类：超过窗口返回 `context_limit`；内存或压力不足返回 `capacity_unavailable`；不支持的精度组合返回 `unsupported_feature`。传输长度问题在派发前明确拒绝，不通过截断原文满足限额。

第一版内存记录可以对整个已验证长度档使用保守固定预留。之后在证据充分时细分 P/G 档位，不必先建复杂的在线回归模型。准备、执行和快照的容量归属保持清楚，不能把当前固定预留与新估算同时重复计费。

## Prefill、输出和等待时间

对相同 BF16 模型分别测量 chunk=64、128、256，选取能满足内存与取消延迟目标的固定配置。初始候选为 128，当前 256 作为对照。这是待测选择，不能声称 chunk 越小整体越快。

小 chunk 减少一次 prefill 的临时张量，并增加检查控制消息的机会。它不减少完整历史 KV，也不消除完整注意力随长序列增加的计算量。在当前串行执行方式下，块间检查也不会自动让其他请求穿插执行。

64K 配置保留 2,048 输出 tokens 时，模板化输入最多为 63,488。128K 配置的对应输入上限为 129,024。更长输出需要减少输入，或使用另一个经过验证的长度组合。用户消息、系统提示和 tools 都计入输入。

长请求的 timeout 根据实测 prefill、生成和清理时间设置，保持客户端、HTTP 链路与服务的超时配置一致。SSE keep-alive 只维持连接，不改变真实 TTFT，也不重置公共 deadline。整段操作仍需可取消，不以无限等待换取通过。

长上下文交互配置先把排队上限设为 2 个请求，超过后明确拒绝。它可以限制重复长文在 CPU 侧的积压，但不会改善正在执行请求的计算速度。需要同时低延迟服务其他用户时，再单独评估调度或额外设备。

传输验收使用中文、代码、长工具结果和接近词表上界的 token ID。先验证现有 1MB 限额能覆盖目标样本；若需扩容，统一修改公共 body、worker frame、准备阶段预算及 Rust/Python fixtures。长度档不能只按“一个 token 等于几个字节”的经验开放。

## 第二阶段：内存仍不足时比较量化

权重量化和 KV 量化分别产生新的执行配置，均保留完整 token 历史，但会改变数值精度。服务不会在请求途中降精度。模型 revision、缓存身份、准入记录和质量结果必须绑定具体配置。

优先比较一个显式 8-bit 权重 bundle 和原 BF16 bundle。权重占当前加载内存的大部分，减少这部分可以给系统和 workspace 留余量。实际节省取决于未量化层、分组元数据及执行临时量，不能直接把 3.505GiB 除以二当作进程占用。4-bit 权重不是第一版的默认选项。

KV 8-bit 是另一个独立候选。固定 MLX-LM 0.31.3 的公开生成接口可以只转换六层 `KVCache`，跳过十八层 `ArraysCache`。按 group=64、BF16 scale/bias 的静态布局，64K 和 128K 的 KV 分别约为 408MiB 和 816MiB，固定循环状态不变。这只估算缓存 payload，没有证明整机峰值或质量收益。

该版本的量化 attention 使用量化矩阵乘、显式 scores 和 softmax。它与 BF16 的 fast SDPA 路径不同。chunk=256、历史长度 128K 时，单份 BF16 scores 的逻辑尺寸就有 512MiB。量化节省的 KV 可能被额外临时空间抵消，因此必须比较完整 prefill 峰值，不能根据 bits 直接做采用决定。

量化候选先检查真实缓存类型、scale dtype、跨扩容边界和 1／2／3／多 token 追加的数值行为，再验证长文任务。既有其他 MLX 版本的原语问题不能直接判定当前 0.32.1 有相同问题，也不能用版本号证明已正确。

仅当新配置保持约定质量，并改善可用内存或延迟时才公开。BF16 路径保留为对照和可选部署；两个配置切换不复用不兼容状态。

## 第三阶段：减少多轮完整原文的重复计算

如果主要耗时来自反复发送同一段长文，增加精确前缀复用。它保留完整原文语义，避免重复 prefill，但不能减少一条活跃请求所需的完整注意力 KV。

实现先覆盖单个可恢复边界，不立即建设通用分页引擎。Qwen3.5 快照同时保存六层 KV、十八层循环／卷积状态，以及准确消费位置和必要的继续执行状态。不能把长 KV 任意裁成短前缀后，继续使用较晚位置的循环状态。

第一版 RAM 快照配额为 0，先验证显式 session 的独占追加，或在独立测试中验证 snapshot restore。随后依据收益设置小配额；例如 256MiB 只适合较短前缀，不足以保留完整 64K BF16 状态。任何长期状态都从请求账原子转入会话或快照账，不把请求结束误当作全部内存释放。

只有 P1b 或 P3 对应能力通过后，才评估 SSD 保存闲置快照。SSD 读取、校验、重建和同步时间必须小于重新 prefill 的时间。恢复时仍预留活动状态和恢复临时空间，避免文件读入与 GPU 状态重建同时挤占内存。

CPU 和 GPU 共享这 16GB 物理内存，CPU offload 不会提供另一份独立 RAM。SSD 快照可以释放闲置状态；把活跃全历史 KV 放到 SSD 则需要逐层读取或专用执行方式，延迟和实现成本不同。第一版不依赖这条路径，也不依赖持续 swap。

通用 `max_kv_size` 对当前模型不能直接产生滑动窗口，因为模型自带 `make_cache()`。即使另行实现滑窗，它也会丢弃部分完整注意力历史，不符合此次默认保留原文的目标。

## 交付顺序与验收

### Kernel 与 serving 的并行工作

Kernel 路线降低每次执行的时间、访存和临时空间。Serving 路线控制需要执行的工作、状态保留时间和总资源占用。两条路线可以并行，但最终通过同一个模型、长度、精度和完整请求测试验收。

当前 HTTP serving 调用 `MLXRuntime`，它加载 `mlx_lm` 并调用 `generate_step`。Supervisor 也检查 provider 为 `mlx-lm`。因此，ApxInf 原生 Rust/Metal kernel 的加速不会自动进入这条服务路径。依据见 [worker 加载](../../python/apxinf/apxinf/serving/text_worker.py#L135)和 [provider 检查](../../crates/apxinf-serving/src/supervisor.rs#L1322)。

近期 serving 工作继续基于已接通的 MLX 路径。原生 kernel 路线在模型级正确性通过后，再接入独立 native worker。该 worker 需要支持准备输入、流式推进、控制处理、真实内存观测和安全结算。Provider 切换需要显式执行身份及独立质量、容量验收，不直接取消现有身份检查。

| 工作 | 具体改变 | 主要收益与限制 |
| --- | --- | --- |
| 请求容量准入 | 按 P/G/chunk 预留状态和 workspace，限制活跃序列及排队字节 | 防止超预算组合进入执行，不会直接减少一个请求的必需状态 |
| 精确会话追加 | 校验历史 token 前缀，在原状态上处理新增输入 | 减少多轮重复 prefill，完整历史仍留在活动状态内 |
| 状态所有权 | 结束时释放请求临时对象，将保留状态原子转交 session | 避免无谓复制、重复记账和提前释放，不依赖通用快照系统 |
| 闲置状态管理 | 按预算逐出可丢弃状态，后续按完整边界保存到 SSD | 减少空闲会话驻留，不减少单个活动请求的全历史 KV |
| 精度配置 | 单独验证权重和 KV 量化，绑定执行身份 | 减少实际存储字节，需要同时通过 workspace 和任务质量验收 |

精确追加优先实现单个显式 session 的独占写入，不同时建设 radix 索引、任意分支和 SSD。假设已有 60K 历史，下轮新增约 1K 输入；只有规范化 token 前缀和全部模型状态位置一致，才可以只 prefill 新增部分。后续 decode 仍需要访问完整历史中的注意力状态。

HTTP 客户端仍可发送完整原文。客户端若不能使用显式 session，则后续通过 stateless prefix lookup 查找已验证的恢复边界。两者不能混用失败语义：显式 session 缺失或版本冲突返回对应错误，stateless prefix miss 才允许重新计算。模板或工具前缀变化时不修改原文来强求命中。

执行 owner 在会话追加期间独占可变状态。成功时原子提交历史、消费位置、状态句柄和版本。发生部分更新后的取消或失败时，未实现回滚的 session 失效。此路径沿用 SS-01 至 SS-08，首版不以双份长状态复制提供隐式回滚。

Serving 侧先完成容量记录与准入，再实现有预算的单会话追加。这两项分别解决长请求能否接纳和多轮是否重复计算的问题。只有测量显示空闲会话或重复文档复用值得投入，才继续 SSD 或自动前缀索引。

| 步骤 | 交付范围 | 通过条件 |
| --- | --- | --- |
| A：明确预算 | 定义内存记录和准入语义，同步必要的契约、类型与原创 fixtures | CPU 检查覆盖超预算、未知配置、长度及字节上限、资源归还 |
| B：64K BF16 | 按 8K、16K、32K、64K 逐级校准，固定 chunk、输出和身份 | 每级容量、取消、清理和质量通过后再进入下一级 |
| C：128K BF16 | 独立部署配置，完整 128K 总窗口 | 峰值、TTFT、decode 速度和桌面压力满足事先冻结的目标 |
| D：可选量化 | 分别比较 8-bit 权重和 KV 8-bit | 数值与任务质量通过，且实际容量或时延收益成立 |
| E：多轮复用 | 根据 workload 选择 P1b 精确追加或 P3 快照，随后考虑 SSD | 真实恢复续写、身份、分支、取消和预算归属通过 |

步骤 A 不跳过现有 P1 内存证据 gate。步骤 E 保持原实施计划中的状态能力依赖。64K 与 128K 各自验收，128K 未通过不妨碍交付已通过的 64K 配置。

每个批准的长度档至少包含以下检查：

1. 比较相同总长度、不同输入和输出比例，包含实际达到输出 allowance 的请求。
2. 覆盖 prefill chunk、KV 扩容边界、末尾取消、EOS、stop 和连续请求清理。
3. 分别记录 allocator active/cache/peak、逐层缓存 payload、进程 footprint、系统压力及 swap 增量。
4. 比较首请求、重复请求和未插桩生产路径，不能把观测同步后的峰值直接当作生产上界。
5. 用独立中文、代码和长文样本测试开头、中间、结尾的信息提取及跨段关联。
6. 验证模型输入保留完整原文，并比较相同配置的直接执行参考与 serving 输出。
7. 验证取消和故障后无未回收子进程，下一条请求能执行，长期状态没有无解释的增长。

质量、TTFT、输出速度、取消延迟和最大内存目标在各项正式采用测试前冻结。原文没有丢失不代表 2B 模型必然能正确利用全部 128K 信息，容量验收和长文任务质量必须分开报告。提前 EOS 的短输出不能冒充完整输出长度验收，加载后被压力阻断的阶段也不能算通过。

本次只完成代码审查、静态计算和方案设计，没有执行模型或 GPU 测试。当前推荐的首个可实施范围是 A 加 B，128K 保留为下一项独立验收目标。

## 外部机制参考

参考仅用于核对公开机制和依赖行为，不作为复制实现的来源。本提案不新增运行时依赖。

- [MLX 统一内存说明](https://ml-explore.github.io/mlx/build/html/usage/unified_memory.html)：CPU/GPU 使用同一物理内存池。
- [MLX 内存限制说明](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_memory_limit.html)：allocator guideline 不等于进程硬内存上限。在线文档为 0.32.3，当前项目仍固定 0.32.1。
- [MLX-LM 长输入机制](https://github.com/ml-explore/mlx-lm#long-prompts-and-generations)：chunk、prompt cache 和 rotating cache 解决不同问题。具体采用范围以本地固定版本为准。
- [固定 MLX-LM attention 路径](https://github.com/ml-explore/mlx-lm/blob/ed1fca4cef15a824c5f1702c80f70b4cffc8e4dd/mlx_lm/models/base.py#L59)：量化 attention 与 fast SDPA 的执行区别。
- [固定 MLX-LM cache 构造](https://github.com/ml-explore/mlx-lm/blob/ed1fca4cef15a824c5f1702c80f70b4cffc8e4dd/mlx_lm/models/cache.py#L15)：模型自有 cache 优先级和量化状态布局。
- [Qwen3.5-2B 配置](https://huggingface.co/Qwen/Qwen3.5-2B/blob/main/config.json)：混合层结构与模型位置配置。容量计算使用本地固定 bundle，线上 main 不替代其身份。
- [vLLM 前缀复用边界](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/#limits)：主要节省共享前缀的 prefill，不减少 decode 工作。ApxInf 混合状态仍需独立实现与验证。
- [SGLang HiCache](https://docs.sglang.io/docs/advanced_features/hicache_design)：参考闲置状态的分层和恢复机制，不照搬独立 GPU／host 内存预算。

检索辅助使用 `metal-kernelwiki`。其中其他版本、其他 dtype 和无模型原语实验只用于选择验证边界，不作为当前 ApxInf 长上下文的正确性或性能结论。
